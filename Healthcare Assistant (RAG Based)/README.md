# Healthcare Assistant - Frontend + Backend Edition

This is a restructured version of the original single-file Streamlit app,
split into a proper **backend** (REST API) and **frontend** (static web UI)
so the two run as separate services that talk over HTTP.

```
healthcare_rag_assistant_app/
├── backend/                  FastAPI REST API
│   ├── main.py                All API routes (/api/chat, /api/health, /api/tips, /api/audit, /api/roles)
│   ├── src/
│   │   ├── config.py            paths + env settings
│   │   ├── database.py          SQLite patient DB (loaded from the CSV)
│   │   ├── llm.py                Groq LLM wrapper
│   │   ├── router.py             Orchestrator: confidence-scored routing + fallback
│   │   ├── sql_agent.py          NL -> SQL over patient records, role-scoped
│   │   ├── rag_agent.py          FAISS retrieval + page-level citations for policies
│   │   ├── access_control.py     SQL validation + role-based column access (RBAC)
│   │   ├── audit.py              Append-only audit log of every access
│   │   ├── safety.py             Emergency screening + response validation/escalation
│   │   └── evaluation.py         Measurable RAG quality metrics + routing confidence
│   ├── data/
│   │   ├── healthcare_dataset.csv
│   │   ├── policies/*.md
│   │   └── audit.db              created at runtime (audit trail)
│   ├── requirements.txt
│   └── .env.example
└── frontend/                 Static web client (no build step)
    ├── index.html
    ├── style.css
    └── app.js
```

## How the pieces talk to each other

- The **backend** does all the work: it loads the patient database, builds
  the FAISS policy index once at startup, screens each question for medical
  emergencies, routes it (patient-record / policy / general) with a
  confidence score, enforces role-based access on patient data, validates
  and safety-checks every generated answer, and logs the access. It exposes:
  - `GET /api/health` – is the API up, is a Groq key connected, DB/audit stats
  - `GET /api/tips` – the currently-rotating health tip
  - `GET /api/roles` – available RBAC roles for a UI role picker
  - `GET /api/audit` – recent audit-log events (who accessed what, when)
  - `POST /api/chat` – send `{ "query": "...", "api_key": "...", "role": "..." }`,
    get back the answer plus routing confidence, safety flags/escalation
    status, and either generated SQL + role-filtered rows (patient
    questions) or numbered citations with page/line-level evidence and RAG
    evaluation metrics (policy questions).
- The **frontend** is a plain HTML/CSS/JS page (no React/build tooling
  needed) with a role selector, confidence badge, citation/evidence panel,
  and an emergency-escalation banner, calling those endpoints with `fetch()`.

## Running it

**1. Backend**

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

The first request that needs the RAG agent will build the policy embedding
index (falls back automatically to TF-IDF if `sentence-transformers` isn't
installed, exactly like the original app).

Optional: copy `.env.example` to `.env` and set `GROQ_API_KEY` so you don't
have to paste it into the sidebar every time.

**2. Frontend**

Any static file server works, e.g.:

```bash
cd frontend
python -m http.server 5500
```

Then open `http://localhost:5500` in your browser.

If your backend runs somewhere other than `http://localhost:8000`, set it
before `app.js` loads, e.g. add this to `index.html` above the `<script
src="app.js">` tag:

```html
<script>window.HEALTHCARE_API_BASE = "https://your-backend-host";</script>
```

## Safety, security & evaluation features

**SQL validation.** Every SQL statement — whether hand-generated by the
fallback template or produced by the LLM — is parsed with `sqlparse` and
checked in `access_control.validate_sql` before it ever reaches SQLite. It
rejects: multiple/stacked statements, comments, `SELECT *`, non-SELECT
statements, references to any table other than `patients`, and any column
not on the current role's allow-list. Failures fall back to a safe
templated query rather than executing anything unvalidated.

**Role-based access control.** Four roles — `admin`, `clinician`,
`billing`, `front_desk` — each map to a column allow-list following the
HIPAA "minimum necessary" principle (e.g. front desk never sees billing or
clinical detail). The role is sent from the frontend's sidebar picker (or
an `X-User-Role` header / `role` field for API callers) and is enforced
both when generating SQL and when filtering the returned rows.

**Audit logging.** `src/audit.py` writes an append-only SQLite log of every
patient-record and policy access: timestamp, user/role, agent, query, the
SQL actually executed, row count, routing confidence, safety flags, and
whether the request was denied/escalated. View recent events at
`GET /api/audit`.

**Routing confidence & fallback.** `src/router.py` scores each keyword
match by how many/how ambiguous the matched terms are. Low-confidence
matches are re-checked with an LLM classifier when available; if nothing
is confident, the router falls back to the general assistant rather than
guessing, and the confidence/method are returned in every response.

**Citations & page-level evidence.** `src/rag_agent.py` tracks the source
file, section heading, and exact line range for every policy chunk. Answers
are prompted to cite `[1]`, `[2]`, ... markers that map 1:1 onto the
returned `sources` list, so every claim can be traced to its exact
passage.

**RAG evaluation metrics.** `src/evaluation.py` computes, on every policy
answer with no extra LLM call: context relevance, groundedness (a
hallucination proxy — how much of the answer is actually backed by
retrieved text), answer relevance, and topic coverage, rolled up into an
`overall_score` plus flags like `possible_hallucination` or
`low_retrieval_confidence`.

**Healthcare safety validation & escalation.** `src/safety.py` screens
incoming questions for emergency language (chest pain, difficulty
breathing, suicidal ideation, stroke symptoms, overdose, etc.) and prepends
an escalation notice with emergency/crisis-line guidance. Generated answers
are also checked on the way out: specific drug dosages are replaced with
"follow label/clinician instructions", definitive diagnosis language is
softened, prescriptive instructions are blocked, and a standard medical
disclaimer is appended to any answer that looks like health advice but
lacks one.

## What changed vs. the original Streamlit app

- **UI moved from Streamlit to hand-written HTML/CSS/JS**, kept visually
  close to the original dark-green dashboard (sidebar with API key + daily
  tip, chat bubbles, expandable SQL/citation panels, recovery tip cards),
  now with a role picker, confidence badge, and escalation banner.
- **State moved from Streamlit session state to the browser**: chat history
  lives in the page's DOM for the session, and the API key/role are
  remembered in `localStorage` instead of Streamlit widgets.
- **The heavy one-time setup (loading the CSV into SQLite, building the
  FAISS policy index) now happens once when the backend process starts**,
  rather than being cached per Streamlit session.
- **Added defense-in-depth around the SQL and RAG agents** (validation,
  RBAC, audit logging, confidence scoring, citations, evaluation metrics,
  and safety/escalation handling) as described above.

## A note on the sample API key

The original project's "How To Run" file included a working Groq API key
inline. That key is not copied into this backend — treat any API key as a
secret, keep it out of anything you commit to GitHub or hand in, and use
`.env` (already git-ignored patterns like `*.env` are recommended) or the
sidebar field instead.
